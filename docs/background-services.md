The orchestrator runs a set of long-running background workers that keep the metadata layer consistent with the backends, handle replication / cleanup / lifecycle, and refresh observability state. All locked tasks apply a random startup jitter of up to half the tick interval before the first tick, preventing thundering herd on the advisory lock when multiple instances start simultaneously. Each interval is counted from the end of the previous tick, so a pass that runs longer than its interval is not followed straight away by another. A tick the database was down for is counted as skipped rather than as a success, so a worker's last success stops advancing during an outage.

## Worker reference

| Task | Interval | Advisory Lock | Description |
|------|----------|:---:|-------------|
| **Usage flush** | configurable (default 30s) | No | Flushes usage counters to the metadata store, refreshes this instance's usage baselines, republishes the fleet-wide gauges, and reloads the cached backend states. The fleet-wide figures - quota bytes, per-backend ledger counts (objects, unverified, plaintext, unreadable, compression, verification coverage) and multipart counts - are read from counters the writes keep, and the queue depths are counted, so every instance reads them itself. Capacity warnings are raised by one instance at a time under advisory lock `1013`, and with Redis a backend is warned for once an hour across the fleet. With Redis, every instance also loads the worker gauges. Runs on every instance in every mode. Adaptive mode shortens interval near limits. Every instance flushes on every tick without a lock; with Redis, each staged batch carries a flush ID the store applies at most once, so a retried flush is not counted twice. Its ticks and health are reported under `usage_flush` like a locked worker's, and a tick where any step failed counts as failed. |
| **Stale multipart cleanup** | 1h | Yes | Aborts multipart uploads older than `cleanup_queue.multipart_stale_timeout` (default 24h) and deletes their temporary part objects. |
| **Cleanup queue** | 1m | Yes | Retries backend object deletions the request path could not complete, with exponential backoff (1m to 24h, max 10 attempts), and reclaims rows whose claim is older than `cleanup_queue.claim_grace_period`, left by a process that died before settling them. Each tick claims due rows 50 at a time, oldest retry first, for up to 20 batches; it stops early on a batch shorter than 50 or one that settles nothing. Rows are settled through the same code the request path uses. On the tenth consecutive failure the row graduates to `cleanup_dlq` for operator action; its bytes stay counted as orphan bytes because they are still on disk. |
| **Rebalancer** | configurable (default 6h) | Yes | Moves objects between backends per strategy. Only runs when enabled. |
| **Replication** | configurable (default 5m) | Yes | Works the [replication queue](replication.md#replication): each tick the replicator creates copies for one batch of under-replicated objects, then the over-replication cleaner removes excess copies from one batch of objects past the factor, and the queue's depths are published to the replication pending gauges. Only runs when `replication.factor` is above 1 or a bucket sets a `replication_factor` of its own, and brings each key to its bucket's factor. Runs once at startup. Its ticks and health are reported under `replication`. |
| **Backend drain** | 10s | Yes | Works every backend whose drain record is in progress: aborts its open multipart uploads, then moves its objects off 100 at a time, smallest first. An object another backend also holds loses only its draining copy, and the rest move to the least-utilized eligible backend. A draining copy that holds the only usable encryption key is kept and the object counts as failed, so the drain cannot complete while it remains. An object that fails to move is passed over for the rest of the pass and retried on the next tick. Once the pass has walked every object, the drain is marked `drained` if no object rows, in-flight intents, or multipart uploads remain, and `failed` with the reason on an error it cannot retry. Does nothing when no drain is in progress. See [draining a backend](operations.md#draining-a-backend). |
| **Lifecycle** | 1h | Yes | Deletes objects matching lifecycle rules whose `created_at` exceeds `expiration_days`. Only runs when rules are configured. Trigger one on demand with `POST /admin/api/lifecycle` or `s3-orchestrator admin lifecycle`. |
| **Reconciler** | configurable (default 24h) | Yes | Diffs each backend's key listing against the object ledger one listing page at a time, classifying every key on the page with a single query and importing objects the ledger is missing. The scheduled pass never removes rows; an on-demand reconcile also removes rows for objects the backend no longer holds. A key whose delete is still outstanding - waiting in `cleanup_queue` or dead-lettered to `cleanup_dlq` - is left alone rather than imported, because those bytes are an orphan awaiting cleanup and importing them would undo the delete. Such keys are logged and counted as `suppressed_pending_cleanup`. An imported object is classified by its bytes: a seek table marks it as compressed and supplies the logical size, since nothing else can once every row for it is gone. One pass covers every virtual bucket sharing the backend. A backend with a drain record is not scanned, so nothing found on it is imported back while it drains or after it has drained. Only runs when `reconcile.enabled: true`. |
| **Pending reaper** | configurable (default 1m) | Yes | Resolves intents whose write never reached its commit. HEADs the destination backend and either promotes the row into `object_locations` (object present) or drops the intent (object absent), which re-queues the key for replication if the intent was holding it at the factor. An intent a newer committed copy superseded has its bytes queued for deletion. A companion intent - an extra PUT copy, a replica, a move, a rewrite or a multipart part - is never promoted: it is kept when a recorded copy sits at its path and otherwise discarded with its bytes. Skips intents younger than `min_age` so in-flight writes are not interrupted. |
| **Scrubber** | `integrity.scrubber_interval` (default 0, disabled) | Yes | Works through the copies least recently verified, re-hashes them, and discards any whose bytes no longer match the stored `content_hash`. The stored form is undone before hashing, in the reverse of the order it was applied - decrypt, then decompress - because `content_hash` covers the bytes the client wrote. A copy it cannot decode at all, such as a compressed copy with no codec configured or an encrypted copy with no encryptor configured, is reported as unreadable rather than corrupt and left alone, since a copy that was never read has not been judged. Only runs when `scrubber_interval > 0`, whether or not `integrity.enabled` is set, since that only decides whether a bucket hashes new objects by default; and only on a tick - never at startup, so an interval longer than the process lifetime means it never runs. Backends that have spent their usage allowance, or reached the share of their egress limit held back by `integrity.scrubber_egress_reserve`, are excluded from the batch and their copies reported as deferred, which leaves the coverage age climbing rather than reporting an unverified fleet as checked. |
| **Notification drainer** | 2s | Yes | Drains `notification_outbox` rows by POSTing CloudEvents JSON to configured webhook endpoints. Optional HMAC signing per endpoint. A row is dropped once its endpoint's `max_retries` are spent. |
| **Backend pressure** | 2s | No | Judges each backend's [pressure](configuration.md#backend_pressure) from the calls this instance timed: a backend with too many calls slower than its baseline, or too many ended by the backend timeout, is tried after the others until its shares fall back. Publishes the judgement the request path reads, the pressure gauges, and an event when a backend comes under pressure or leaves it. Runs on every instance in every mode without a lock, since each instance judges from its own calls. Its ticks and health are reported under `backend_pressure`. |
| **CB watchdog** | 5s | No | Probes every registered circuit breaker. An open breaker runs its own check once it is due and closes when the check passes, so recovery does not wait for client traffic: the database breaker pings the database every open timeout, and each of a backend's breakers - the backend breaker and one per call - checks the backend on a doubling backoff. |

## Manual triggers

Every worker above can be run on demand rather than waited for, from the admin API, `adminctl` and the TUI: rebalance, replicate, over-replication, scrub, backfill-checksums, reconcile, usage-flush and lifecycle. The dashboard offers all of them except reconcile and usage-flush.

A manual pass takes the advisory lock its scheduled service holds, so it never overlaps a scheduled one: rebalance, replicate, over-replication, a rebuild of the replication queue, scrub and reconcile are each skipped with `a <name> pass is already running` while the lock is held, without waiting for it. Lifecycle is the exception. Its sweep is idempotent - a repeated delete of the same key is a no-op - so a manual sweep may overlap a scheduled one and costs a little duplicated work rather than correctness.

The passes with no scheduled service hold locks of their own, so two manual runs - from two instances, or from the admin API and the dashboard at once - cannot overlap either. The four conversion passes and key rotation share lock `1015`, so a conversion never moves a copy another one is rewriting, and a run that finds it held is refused with `409`. Backfill-checksums holds lock `1016` and is skipped while another backfill runs, since a second one would read every unhashed copy again. The unreadable-copy purge reads no bytes and dropping an already-dropped copy changes nothing, so it takes no lock.

Lifecycle is the one where this matters most in practice. Its tick is hourly and a restart adds up to half that again as jitter, so a rule you have just written can take 90 minutes to prove itself. Until it runs, a rule that matches nothing looks exactly like a rule that ran and found nothing expired; the trigger reports deleted and failed counts separately so you can tell those apart immediately.

## Concurrency

Background services (rebalancer, replicator, over-replication cleaner, cleanup queue) share the admission pool with HTTP requests, so `max_concurrent_requests` is the total budget for both HTTP and background backend operations. Background work waits for slots in a queue of its own beside each virtual bucket's, takes its turn at freed slots the same way, and never holds more than half the pool. On a busy pool it gets a share like any one virtual bucket, and the rest go to clients. Replication, drain and cleanup slow down while clients keep the pool full.

## Multi-instance behavior

The advisory locks are PostgreSQL session-scoped - if one instance holds the lock for a task, other instances skip that tick silently. Each task runs on exactly one instance at any moment. SQLite runs a single instance and holds one in-process lock per ID, so a long pass of one worker never delays another's tick. The usage flush is not locked, since each instance flushes its own counters, and neither are the CB watchdog, which acts on each instance's own breaker state, or the backend pressure tick, which judges from each instance's own calls.

See [docs/deployment.md](deployment.md) for the multi-instance deployment model.
